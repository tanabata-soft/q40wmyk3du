# 新しいアルバムの作り方（量産手順）

デジタルCDアルバムは「エンジン（仕組み）」と「データ（作品）」を分けてある。新しいアルバム（NK-002、NK-003…）は、エンジンに触らず、データの差し替えだけで作る。

**エンジンの正本はこのテンプレート repo（`mmishina-art/digitalcd-engine`、非公開）である。新作はこの repo をコピーして作る。** 以下の手順は、特に断らない限りコピー先の作品 repo での作業を指す。

この文書は2部構成。**前半「素材の用意」**で、Google Drive のフォルダ（曲ファイル一式）から `src/album/` に流し込める形の素材を作る。**後半「エンジンとデータの境目」「手順」**で、リポジトリへ流し込んで公開する。

シングル形態（デジタルシングルCD：最大3曲。表題曲＋カップリング＋任意のボーナストラック）の仕様は `docs/SINGLE.md` に置く。制作の流れはこの文書をそのまま縮小適用する。

## 素材の用意（Google Drive のフォルダから）

1アルバム分の曲ファイルが入ったフォルダを、そのアルバムの入力とみなす。入力形式は問わない（次項）。

**大原則: 足りないものがあっても止まらず、あるもので作り切る。** 欠けた素材は、その場で用意できる最善の代用品で**仮置き**し、アルバムとして完成させる。仮置きした箇所は「仮置きリスト」に残し、完成物と一緒に提示する（差し替えや確定は、後からそのリストに対して行えばよい）。オーナーの確認ポイントは3か所ある（①ストーリーと曲順、②ジャケット候補、③歌詞の漢字の最終確認）が、どれも進行を止める関門ではない。確認が取れない場合は推奨案を採用して進め、仮置きリストに載せる。

0. **入力検証と入口変換（音源の一本化）**: フォルダ内のメディアファイルを列挙する。形式は mp4 に限らない（mp3 / wav / flac / m4a などの音声ファイル、mov / webm などの動画ファイルも可）。ffprobe で再生時間と、音声・字幕ストリームの有無を確かめる。**受け取った曲ファイルは、制作の入口で音声を抽出して MP3 192kbps に変換し、それをその曲の唯一の正規の曲ファイルとする**（単位B、2026-11-25 オーナー決定）。プレイヤー（`src/album/assets/audio/trackNN.mp3`）／リズムゲーム（`src/game/assets/trackNN.mp3`）／譜面生成器の解析は、すべてこの1本を参照する（プレイヤー側とゲーム側に同一バイトのコピーを置き、ビルドでは内容ハッシュが同一のため dist 上は1ファイルにまとまる）。**受け取り時の元ファイル（MP4 等）はアプリに同梱しない**（素材フォルダ側に保管するだけ）。変換の前に、元ファイルから (a) 字幕（歌詞 sync の元。MP3 化すると失われる）と (b) 各曲の代表フレーム（曲画像の候補。動画がある場合）を先に抽出しておくこと。フォルダ内に歌詞テキスト・画像・メモなどの付属ファイルがあれば、それも素材として取り込む（既にある歌詞やジャケット絵は、作り直さずそのまま使う）。判別できないファイルは対象外として進め、仮置きリストに残す。
1. **歌詞の読み取り**: 歌詞データ（sync.ts）の元を、次の優先順で用意する。(1) ファイルに字幕があれば抽出する。(2) 曲名（と歌手名）が分かれば、ネットで歌詞や公式情報を調べて補完・照合に使う。(3) どちらも無ければ、文字起こしで仮の歌詞を作る。字幕がローマ字のみの曲は日本語表記に変換する。漢字の当て方で迷う箇所は断定せず「要確認」として仮置きリストに残す。字幕以外の経路で得た歌詞には行ごとの開始時刻が無いので、文字起こしのセグメントと照合して時刻を付ける（NK-001 のハイライト補正と同じ方法）。どの経路でも、最終の読みの確定は耳の仕事（仮のまま完成させてよい）。
2. **メタデータの整え**: 表示タイトルを決める（ファイル名のままにしない。正式な表記に整える）、ジャンルを付ける、再生時間を実測で確定する。曲名が分かれば、ネットの情報（ジャンル、歌手、発表時の情報など）でも補完する。出典のはっきりしない情報は仮置きリストに載せる。歌詞データのキー（tracks.ts の `src`）もここで決める。
3. **ストーリーと曲順【確認ポイント①】**: 全曲の歌詞から、アルバム全体の物語（コンセプト）を組み立て、それに沿って曲順を決める。ジャンルの流れと再生時間のバランスも見る。確認が取れればそれを正とし、取れない場合は推奨のストーリーと曲順で進めて仮置きリストに載せる（ここが後で変わると文章もジャケットも手戻りになるので、リストの中では最優先で確定してもらう）。
4. **ブックレット文章**: ライナーノーツ（見出し2つ）と、曲ごとの解説（歌詞とストーリーに沿って書く）、奥付を用意する。カタログ番号は NK-002 以降の連番を付番する。
5. **曲画像**: フォルダ内に曲の画像が既にあれば、それを優先して使う。映像のある曲は 0 で抽出したフレームを基本にする（`trackNN.jpg`）。音声のみの入力や、映像のない・使えない曲は、歌のイメージに合わせて生成する（音声ファイルだけのアルバムでは、生成が既定の経路になる）。
6. **ジャケット一式**: 表ジャケットと背景は、アルバム全体のイメージで複数候補を作り、オーナーが選ぶ【確認ポイント②】。選択が無い場合は推奨候補を採用し、仮置きリストに載せる。裏ジャケットは曲画像のモザイクで自動生成する。アプリアイコンは表ジャケットから作る（`scripts/make-icons.mjs` のコメントの手順）。表ジャケットの様式は `docs/ALBUM-DESIGN-STUDY.md` の型（型A〜J）から作品の性格に合わせて1つ選び、タイトル配置・書体・色彩・帯の扱いなどのパラメータを型の定義で決める。
7. **時刻の検証と歌詞の確定**: 歌詞の開始時刻が実際の歌い出しと合っているかをサンプル照合で確かめる。等間隔の人工的な時刻が付いている素材はずれている前提で、文字起こしとの照合で補正する（NK-001 で実際に必要だった）。漢字の「要確認」はオーナーの耳で確定する【確認ポイント③】。確定しなくてもアルバムは完成として扱い、未確定分は仮置きリストに残す。

そろった素材は、次の「エンジンとデータの境目」の形に置く。**納品・公開の報告には、仮置きリスト（仮置きした箇所と、その理由・代用品の内容）を必ず添える。**

### 素材まわりの実務メモ

- **受け取りの現行形**: 曲の生成はオーナーが自分の Gemini アプリ（AI Pro）で行い、チャットへ MP4 をアップロードするのが標準の受け取り方。Google Drive フォルダ経由で渡された場合も、以降の手順は同じ。 受け取った MP4 は入口変換（「素材の用意」0）で MP3 192kbps に変換して唯一の正規音源とし、MP4 はアプリに同梱しない。
- **動画末尾の処理**: Gemini 生成の動画は、末尾にロゴのアウトロ映像が付くことがある。音声側の音楽終了点（フェードアウトの終わり）を実測してそこで切り、末尾の無音も詰める。表示上の尺はプレイヤーの表示に合わせて確定する（NK-S004 で実施）。
- **歌詞の時刻付けの検証**: 字幕の表示時刻は信用しきらない。付けた開始時刻は、単語レベルの文字起こし（faster-whisper small、VAD なし）で照合し、確定前に別モデル（medium）のフレーズ境界時刻と突き合わせる（片方だけでは全体のずれを見逃す。NK-S003 では約7〜12秒のずれが実際にあった）。字幕のウィンドウが後半で実歌より遅れることや、字幕が抜ける区間があること（その区間も歌は続いている）がある。抜けた行は文字起こしから補い、補った行とその時刻は仮置きリストに明記する。
- **インスト曲の扱い**: 歌詞のない曲は `sync.ts` に空配列を入れて成立する。その場合は、歌詞前提の内容チェック（`scripts/content-checks.mjs`）と単体テストの歌詞長の前提を、インスト契約に合わせて調整する（実施例は NK-S004 のリポジトリ）。
- **単体プレビューの音源キャッシュ**: `npm run build:preview` はプレビュー用に音源を再エンコードし、`node_modules/.cache` にキャッシュする。新作では build:preview の前にこのキャッシュを消す。前作の同名ファイルが残っていると、前作の音源が埋め込まれる事故が実際に起きた。プレビューを渡す前に、埋め込まれた音源の長さを実測して確かめる。

## エンジンとデータの境目

- **エンジン（作品ごとに触らない）**: `src/` のうち `src/album/` 以外（main.ts / logic.ts / style.css / pwa.ts / install.ts / debug.ts）、`index.html`、`public/boot.js`、`scripts/`、`vite.config.ts` の仕組み部分。
- **データ（作品ごとに差し替える）**: `src/album/` の中身ぜんぶ。
  - `album.ts`: 題名、カタログ番号、ライナーノーツ（本文と見出し）、奥付の文面。
  - `tracks.ts`: 曲目（題名・ジャンル・再生時間・解説、`src` は歌詞データのキー）。並びが曲順。
  - `sync.ts`: 歌詞の同期データ（生成物）。形は `{ "曲のsrc": [[開始秒, "歌詞"], ...] }`、キーは `tracks.ts` の `src` と一致させる。時刻は単調増加。
  - `media.ts`: 曲ごとの画像・音源の対応表。曲数分の import を並べ、`TRACK_IMG` / `TRACK_AUDIO` を曲順に export する。
  - `assets/img/`: 固定の置き場所（スロット）が決まっている。
    - `jacket.jpg`（表ジャケット）、`back.jpg`（裏ジャケット）、`bg.jpg`（背景）
    - `track01.jpg` 〜 `trackNN.jpg`（曲ごとの絵。NN は2桁ゼロ埋め、曲数分）
  - `assets/audio/`: `track01.mp3` 〜 `trackNN.mp3`（曲順。入口変換で作った唯一の正規音源 MP3 192kbps。リズムゲーム側 `src/game/assets/trackNN.mp3` と同一バイトで、プレイヤーとゲームが同じ音源を共有する）
- **リズムゲームの作品データ（付ける場合だけ）**: `src/game/songs.ts`（曲リスト）、`src/game/data/`（譜面・歌詞。生成物）、`src/game/assets/`（ゲーム用音源・ジャケット）。`src/game/` のそれ以外と `index.html` の `#view-game` はエンジン側。詳細は下の「リズムゲーム（任意モジュール）」。

## 手順

1. **リポジトリを用意する。** テンプレート repo（`mmishina-art/digitalcd-engine`）をコピーして、新しいリポジトリを作る（GitHub で新規作成し、中身を移す）。**置き場所は配布用 Organization `tanabata-soft` の下、名前は作品名を含まないランダムな文字列にする**（URLから作品や持ち主が分からないようにするため。オーナー指示 2026-11-04）。作品とリポジトリ名・URLの対応は各リポジトリの `docs/HANDOVER.md` に残す。
2. **アプリ ID と版数を変える。** `package.json` の `name` を新しい ID に（例: `kiso-album-2`。**既存のアルバムと別の名前にすること**。同じ `tanabata-soft.github.io` に載るため、同じ ID だと保存データや Service Worker のキャッシュが混ざる）、`version` はゲームなしなら `1.0.0`、リズムゲーム対応なら `2.0.0` にする。`engineVersion` はコピー元テンプレートの版数のまま保持する（裏ジャケット脚注に併記するエンジン版数の正本）。
3. **`src/album/` を差し替える。** 上の境目に沿って、album.ts / tracks.ts / sync.ts / media.ts / assets を新しい作品の内容にする。`sync.ts` は前半「素材の用意」の手順で作る（作り直しの詳細は `docs/HANDOVER.md`）。
4. **アプリ名と色を付け替える（2か所ルール）。** `vite.config.ts` の `APP_NAME` / `THEME_COLOR` / `BACKGROUND_COLOR` と、`index.html` の `<title>` / `theme-color` / `apple-mobile-web-app-title` を新しいアルバムに合わせる（`npm run check:content` が一致を確かめる）。テーマ色に合わせて `src/style.css` の `:root` の色（`--indigo` など）も変えてよい（ここはエンジン側だが、配色は作品の世界観の一部として付け替え対象とする）。
   - **ホーム画面の名前は `APP_NAME` で決まる。** `APP_NAME` は manifest の `name`／`short_name` そのもので、ホーム画面のアイコン名になる。作品名そのもの（例: `Flavor`）を入れ、`index.html` の `<title>` と `apple-mobile-web-app-title` は「APP_NAME ― 形式名」の形にする。manifest の `description` と `index.html` の meta description も、テンプレートの雛形文言のままにせず作品の説明文に差し替える。仮名が残るとアイコン名が「テンプレート」になる事故が実際に起きた（NK-S009 v1.0.0）。`check:content` の manifest-name 検査が、仮名の残存と `APP_NAME` と作品名（`src/album/album.ts` の `ALBUM.title`）の食い違いを止める（テンプレート本体の雛形データだけは対象外）。
5. **アイコンを作り直す。** 新しい `jacket.jpg` から、`scripts/make-icons.mjs` のコメントの手順で `public/icons/` の4点を置き換える（`npm run icons` で寸法を確認）。
6. **画面テストの期待値を合わせる。** `e2e/app.spec.ts` の曲数・ブックレットのページ数（曲数+3）・曲タイトルなどを、新しい収録内容に直す。`scripts/shots.mjs` はテンプレートではシングル形態用（撮影対象は表・裏・再生・インストール）になっている。アルバム形態では、曲目画面とブックレット画面の撮影と、トップ画面のインストール入口（`#install-open-cover`）を対象に戻す。
7. **確かめる。** `npm run verify`（lint・単体テスト・ビルド・PWA成立・内容整合）と `npm run test:e2e`、`npm run shots`（`shots/all.png` で見た目を確認）を通す。作業中の確認は `npm run build:preview` の単一 HTML で。
8. **公開する。** 新しいリポジトリの Settings → Pages → Source を **GitHub Actions** にし、`main` の保護ルール（`protect-main`: PR必須、status checks `check` と `e2e`、force push禁止）を設定する。作業は feature ブランチ → PR → CI が通ったらマージ（既定の流れ）。
9. **台帳レポートを送る。** 【デジタルCD台帳反映用レポート】を、制作開始時・公開時・状態変化時の3回、オーナーへ送る（詳細は `docs/HANDOVER-BRIEF.md` の「台帳レポート」）。同じ内容をその作品の `docs/HANDOVER.md` にも残す。

## 注意

- 公開済みのアルバムは、それぞれ独立したリポジトリとアプリ ID を持つ。エンジン側の直しは公開済みの作品に自動では効かない（作品が壊れないための割り切り）。同じ直しを複数作に当てるときは、各リポジトリに同じ変更を入れる。
- **裏面の下絵（back.jpg）のなじませ（オーナー指示 2026-11-04）**: 裏面の下絵に曲ジャケットを並べるときは、ジャケットに焼き込まれた白枠・紙枠・額縁マットをそのまま使わない。枠の厚みを実測して内側の絵だけを切り出し、上下の継ぎ目にはクロスフェード（目安90px）を入れてなじませる（NK-S002 v1.1.1、NK-S003 v1.0.2 で実施）。再生画面の曲ジャケット（trackNN.jpg）自体は元のままでよい。シングルの下絵に使う絵は1曲目・2曲目のみで、ボーナストラックの絵は入れない（2026-11-12 基本ルール、詳細は `docs/SINGLE.md`）。シングルの裏面パネルはスクロールなしで収まることも基本ルール（同 SINGLE.md）。
- Netlify は使わない（公開はすべて GitHub Pages に一本化。2026-11-10 決定）。
- **歌詞タップでその行から再生**（アルバム・シングル共通。オーナー指示 2026-11-12）: 再生画面の歌詞行をタップすると、その行の開始時刻へシークして再生する。ドラッグによる歌詞スクロールではシークしない（タップ判定は移動量とスクロール量で分ける）。

## リズムゲーム（任意モジュール）

CD の収録曲で遊ぶリズムゲームを、アプリ内モードとして同居させる任意モジュール。2026-11-20 のオーナー決定で、独立エンジン（旧 `mmishina-art/rhythm-game-engine`）から CD エンジンの一機能に統合した（素材は NK-S003 で実働した版）。**モード名は作品ごとに付けず「リズムゲーム」で統一する**（オーナー決定 2026-11-20）。入口はトップ画面の「遊ぶ」ボタンで、入ると CD 側の再生は止まる。

- **境目**: エンジン = `src/game/` のコード一式、`index.html` の `#view-game`、`src/main.ts` の入口配線、`src/debug.ts` の操作追加登録（`registerDebugActions`）。作品データ = `src/game/songs.ts`、`src/game/data/`（生成物）、`src/game/assets/`（ゲーム用音源・ジャケット。ヒット音 `hit-sample.wav` と結果ボイス2種 `voice-fullcombo.mp3` / `voice-newrecord.mp3` はエンジン同梱の共通素材）。
- **付けない作品では**: `src/game/` と `#view-game` と「遊ぶ」ボタンを取り除き、`src/main.ts` の配線、`e2e/game.spec.ts`、`tests/game-data.test.ts`、ゲーム用スクリプト（`generate-charts.py` / `gen-game-lyrics.mjs` / `check-two-thumb.py` / `verify-autoplay-full.mjs` / `make-sample-game-audio.py`）も一緒に除く。
- **制作手順**（CD 側の素材がそろってから）:
  1. **音源とジャケット**: 音源は入口変換で作った唯一の正規音源をそのまま使う。CD 側の `src/album/assets/audio/track0N.mp3` を `src/game/assets/track0N.mp3` へ同一バイトでコピーする（変換はしない。ゲーム側の MP3 が譜面タイミングの基準なので、再エンコードで作り直さない）。ジャケットは `src/album/assets/img/track0N.jpg` を `src/game/assets/` へコピーする。
  2. **曲リスト**: `src/game/songs.ts` に曲 ID・album・genre を書く。frameInset（ジャケット絵の四辺に焼き込まれた紙枠の実測幅。枠が無い絵は 0。ゲーム中の絵と選曲画面のスライドの両方で、この幅ぶん枠を切り抜いて表示する）と slidePosition（カルーセルでのジャケットの寄せ。必要な曲だけ）もここで決める。bonus（ボーナストラックなら true。CD 側 tracks.ts の bonus と一致させる。スライドに金色の BONUS チップが出る）もここで決める。accent（曲のテーマ色）もここで決める。テーマ色はパターン3（曲ごとに切り替え）で確定（オーナー決定 2026-11-20）: 各曲のジャケットから `python3 scripts/jacket-accent.py src/game/assets/track01.jpg` で抜き出して書く（視認性のための明度・彩度の持ち上げ込み）。選曲に合わせてメニューの枠・光・ボタンなどのアクセント色が切り替わる。モノクロジャケットなど色が取れない場合は、作品の文脈に沿って手で選んでよい（NK-S009 の例あり）。なお同日、一時「表紙ジャケットの色で1色固定」も検討され v1.3.0 で実装したが、NK-S009 の実機評価を経てパターン3に確定し、v1.4.0 で戻した。

### 演奏まわりの標準仕様（NK-001 の実機フィードバックで確立、エンジン v1.5.0 で標準化）

- **画面収まり**: `.game-main` は `width: 100%` ＋縦 flex（margin の auto だけだと flex の stretch が効かず幅が 480px に張り付く）。メニュー画面も縦 flex で、高さが足りないときはカルーセルだけが縮み、他の部品は元の大きさで一画面に収まる。
- **広い画面（幅 481px 以上）**: プレイ画面はスマホ比率 390:844 のステージにして中央に置く（オーナー決定 2026-11-21「案B」）。レーン幅もノーツの落下距離も比率までスマホと一致させる。余白は単色、ステージに薄い影。歌詞の top はステージ高さ比（46.2085% = 390/844）＋10px。
- **中断は確認カードで統一**: 左上のボタンは「❚❚ 中断」のピル型。ボタン・アプリ切替（画面が隠れる）・PC の Esc のどれでも、演奏を凍結して確認カード（#pause-screen）を出す。「つづける」は READY 1秒をはさんで再開、「はじめからやりなおす」は確認なしで同じ曲を頭から開始し直し、「メニューに戻る」はスコアを記録せずメニューへ。凍結は AudioContext の suspend ではなく「曲位置を保持して音源を止め、再開時にその位置から鳴らし直す」方式（ループの音声時計凍結検知・自動 resume と suspend が競合するため）。
- **音声時計の凍結はまずポーズ**（オーナー決定 2026-11-24、2026-11-20 の「無理に再開せず初期化再スタート」方針を置き換え）: 演奏中に音声時計（currentTime）が壁時計1.5秒止まったら、即座に打ち切らず中断確認カードでポーズする。時計は iOS の音声割り込み（着信・Siri・通知等）でも1.5秒以上止まるのが普通で、旧方針ではそのたびに演奏が捨てられプレイ中に曲選択へ戻ってしまった。曲位置は時計基準で保持されるため、時計が復帰すれば「つづける」で止めた位置から再開できる（自動では再開しない）。ポーズ中は凍結検知の対象外とし、手動ポーズは打ち切りの対象にしない。凍結が原因のポーズに限り、時計が復帰しないまま10秒（FREEZE_PAUSE_ABORT_MS）経過したら、最後の手段として AudioContext を作り直してメニューへ戻す。開始時の壊れた context 作り直しと READY 中の開始初期化し直しは従来どおり。
- **端スワイプ対策**: ゲームモード中は履歴を1つ積んで popstate を捕捉し、「戻る」でもアプリを閉じさせない。2026-11-24 のオーナー決定で、プレイ中の「戻る」は確認カードを出さず**完全無効化**（遷移を消費して積み直すだけ）に変更した（iPhone の左端スワイプ誤発で演奏が止まるのを防ぐ。中断の導線は画面内の中断ボタンと Esc に一本化）。あわせて、レーン領域（ノーツ落下・タッチ判定の範囲）は画面／ステージ幅の中央に縮小し、片側約20px（390px幅基準。`LANE_MARGIN_RATIO = 20/390`）の余白を両脇に取る（オーナー決定 2026-11-24、全端末共通のレイアウト。機種別分岐にしない）。余白は無反応地帯で、タッチしても入力にならず、フリックの始点にもならない。画面端の操作（iOS の左端スワイプ、Android のジェスチャナビゲーション）の誤爆を元から減らすのが狙い。ノーツ幅・フリック矢印（レーン幅−10px の規則は維持）・タッチの X→レーン変換・判定ラインは新しいレーン形状に従い、判定ラインの高さ（HIT_Y_RATIO）と落下時間は変えない。ワイド画面のステージ表示（案B）でもステージ内に同じ比率の余白を取る。ビジュアライザー領域（390基準 x 58..332）はレーン領域（同 x 20..370）より内側で矛盾しないため変更しない。入場時のフルスクリーン試行は **Android のみ**（端スワイプ対策が目的なので、ジェスチャーナビゲーションの無い PC 等では全画面にしない。オーナー決定 2026-11-21）。あわせてフルスクリーンはゲーム画面だけに留める（CD 側の画面には広げない）。ゲームから出るときは `exitGameMode()` で履歴ガードの掃除とフルスクリーン解除をする（`src/main.ts` の `go()` で、game 画面から離れるときに呼ぶよう配線済み）。
- **開始直後の残像消去**: `start()` の冒頭（音源の読み込み前）で、両キャンバスを地の色（#0e1018）に戻し、歌詞表示（DOM の3行）にも「歌詞なし」を通知して消す。キャンバスの消去は変換行列を外して実ピクセル全面を塗ること（CSS 単位で塗ると端数で右端・下端1ピクセルに残る）。**残像対策はキャンバスと DOM 表示の両方を見ること**（歌詞は DOM なのでキャンバス消去では消えない。NK-001 v1.2.9 の教訓）。
- **選曲メニューの背景**: 選曲と同時に差し替える。フェードアウト＋遅延の差し替えは、前の曲の背景が一瞬残るのでしない。未読込のときだけ読み終わってから差し替える。
- **結果発表ジングル**: 演奏が終わったら、まず標準素材のジングル（sound.ts の `playResultJingle`、`src/game/assets/result-jingle.mp3`。NK-S006 でオーナーが提供した音源ファイルを v1.8.1 で共通仕様化）を鳴らし始め、`resultJingleDurationMs`（通常 1260ms／S ランク 1480ms。旧・合成ジングルの長さを引き継いだ待ち時間）だけ待ってから結果カードを出す（素材は 3.0 秒あり、カードが出たあとも鳴り続ける）。効果音オフのときは鳴らさず結果を即表示する。

### frameInset（紙枠）の測り方 — 必ず目視と実測の両方で

紙枠の見逃しは繰り返し起きている（NK-S006『胸を張って笑え』38px、NK-001『ニコラスケイジと木曽と私』17px。どちらも「枠なし」で一度公開された）。さらに NK-001 v1.2.4 では、無彩色の白枠（track06『Kiso Night Silhouette』31px）が暖色の紙色テストをすり抜けて見逃され、track04 も四辺実測で 17→24 へ上げ直した。**端の画素のばらつき（標準偏差）だけの判定は使わない**。紙の質感がある枠はばらつきが大きく、「均一な帯」と判定できないためである。次の手順で決める。

1. **全曲のジャケットをサムネイルで目視する**（1曲でも省かない）。四辺に均一な幅の帯が見え、内側の角が丸く・境界が直線的なら枠を疑う。
2. **紙色バンドの実測で裏を取る**: 端から内側へ数 px ごとの列（行）を取り、「紙色」（ベージュ〜クリーム。目安は R−B が 22 より大、R が 85〜215）の画素の割合を出す。**本物の枠は、割合がほぼ 1.0 のまま帯の幅だけ続き、絵の境界で 0 近くへ急に落ちる**。
   **無彩色の白枠は暖色テストでは検出できない**（R−B が小さいため「絵の一部」に見える）。白〜無彩色の明るい画素（彩度が低く明度が高い）の割合でも同じ測り方をし、帯状にほぼ 1.0 が続いて境界で急に落ちれば白枠と判定する。ポスター風の白い縁取りが焼き込まれている絵が典型（NK-001 track06）。
   **幅は四辺すべてを測り、その最大値で決める**（frameInset は四辺一律に効くため）。辺ごとに非対称なことが普通にある（track06 は右 29px・上 14px・下 4px・左 3px で、最大の辺に合わせて 31。track04 は左・上だけで決めた 17 では右辺の紙が残り、24 に上げ直した）。
3. **絵柄と区別する**: 雪・煙・水面などの明るい絵柄や、擦れ・汚しの質感は、割合がだらだらと下がり境界が曖昧で、四辺そろわない。これらは枠ではないので 0 のままにする（NK-001 の『木曽路のニコラス』『凍える銀の幕』がこの型）。ポスター全面の地の色（クリーム地など）も、帯として境界で落ちないので枠ではない（NK-001 track02）。
4. 決めたら `songs.ts` に根拠をコメントで残す（実測方法と値）。設定した曲は、選曲スライドと演奏画面の両方で枠が消えたことを実描画のスクリーンショットで確認してから公開する（frameInset は両方に効く。エンジン v1.4.1 以降）。

### 譜面生成で落ちたとき

- `charts.json` は**全曲そろったときだけ一括で書かれる**。途中の曲で検証（レーン割合など）に落ちると、ファイル自体が出ない。落ちた曲より前の曲は生成・検証まで通っているので、生成ログの曲別結果（BPM・ノーツ数）を控えておく。
- 直し方は2通り: その曲だけの調整（生成器の曲別パラメータ。レイヤーの寄せ、同時押しの間引きなど）か、生成器の配分ロジック自体の見直し。どちらでも**譜面ファイルの手編集はしない**。再生成したら両親指チェック（`python3 scripts/check-two-thumb.py src/game/data/charts.json`、パスは引数で渡す）まで通す。
- 歌詞の生成（`gen-game-lyrics.mjs`）は譜面の後。譜面の長さで歌詞の終わりを締めるため、順序を逆にしない。`sync.ts` が `[秒, "歌詞"]` のタプル形式でもそのまま使える。

### 検証の実務（この VM 固有の注意）

- **e2e の前に 4173 番ポートの持ち主を確認する**。他ワークツリーのプレビューが掴んでいると、古いビルドに対してテストが走り、失敗の切り分けを狂わせる。配信中の版数や文言で、自分のビルドであることを確かめる。ポートが空いていないときは使い捨てのローカル設定（別ポート・reuseExistingServer 無効）で回し、その設定ファイルはコミットしない。
- 単体テストの layer-rules は制限時間 5 秒で、VM の負荷が高いと時間切れで落ちる既知の揺れがある。疑わしいときは `--testTimeout` を延ばして単独で回し、本体が通るかで切り分ける。
- **完走確認の時間**: この VM のヘッドレス再生は、負荷時に実時間の半分前後まで遅くなることがある。標準の `verify-autoplay-full.mjs`（制限時間＝曲の長さ＋90秒）が時間切れになっても、譜面の欠陥とは限らない。切り分けは、実績のある既公開作品でも同じ遅れが出るかを見る。収まらないときは1曲ずつ、曲の長さの2倍以上の制限で回して全曲フルコンボを確認し、その旨を HANDOVER に残す。
- **単体プレビュー（HTML 1ファイル）を作るとき**: 先に `node_modules/.cache` を消す。再エンコード済み音源のキャッシュに前作の同名ファイルが残っていると、そのまま埋め込まれて「曲が違う」事故になる。完成後は埋め込まれた音源を取り出して長さを実測し、原曲と一致を見てから渡す。
- **配信確認**: 公開ページの HTML からバンドル名（`assets/index-*.js`）を取り、ローカルビルドのものと一致するかで見る。一致しないときはキャッシュの古さかデプロイ待ちなので、取り直して確かめる。

### 公開の型

機能ブランチ → PR → CI（check・e2e の両方）→ squash マージ → 配信確認 → 作品の `docs/HANDOVER.md` に記録 → 台帳チャットへ報告。版数（`package.json` の version）は公開のたびに上げ、報告に明記する。報告には、その作品が取り込んだテンプレート（エンジン）の版数も併記し、dist 合計サイズも記録する。公開済み作品の HANDOVER の台帳ブロック（版数・状態）も同じ変更で更新する。

## 表ジャケットと裏面のルール（2026-11-05 オーナー決定、NK-001 で確立）

### 表ジャケット
- 題材はライナーノーツの世界観から決める。生成絵に文字は描き込まず、タイトルは後付けで合成する。
- タイトルの配置は、ホーム画面アイコン（角丸・円形マスク・小サイズ表示）で欠けない範囲に収める。アイコンプレビューで先に確認する。

### 裏面（曲ジャケットのモザイク。シングル裏面の「2曲結合＋クロスフェード」とは別形式のルール）
- **グリッドは曲数で判断する**：〜9曲＝3列×3段（1マス 600×600）、10〜12曲＝3列×4段（600×450）か 4列×3段（450×600）、13〜16曲＝4列×4段（450×450）。12マスの2形式は、曲絵の構図（上下を切るか左右を切るか）で選ぶ。
- **マスが余ったら、最下段側の余りマスをタイトル面が埋める**。タイトルだけは例外で、余った面積を埋めるサイズにする。
- **駒は曲の絵だけ**。曲でない絵（背景用の風景画など）は駒として入れない。ただしタイトル面の背景に使うのは可（作品の背景絵＋半透明の暗幕で文字を立てる）。
- 各曲の絵は**判型いっぱいにトリミング**して入れる。縮小して全体を見せる方式（自分の絵のぼかし背景つき）はしない。結果として**曲タイトルが切れてもよい**。
- マス同士は**隙間なくみっちり突き合わせる**。溝（ガター）もフェードも入れない。
- 曲ジャケットに焼き込まれた白枠・紙枠は、**輝度プロファイルで深さを実測して切り落とす**（例：右30px・上15px）。再生画面の曲画像は元のまま使う。
- **曲目リストは裏面に印刷として入れる**（全曲・曲順どおり・時間入り、ボーナストラックは BONUS 表記、絵のない曲もリストには載せる）。表示専用で、ここからジャンプはさせない。印刷した作品は `album.ts` の `printedBackList` を true にして、アプリ側の重ねリストと一本化する。
- **裏ジャケット画面の脚注（`#bc-foot`）には、奥付（カタログ番号／形式名）と並べて、作品版数とエンジン版数を併記する**（オーナー指示 2026-11-25。例：「NK-S001 ／ デジタルシングルCD ／ v2.0.0 ／ エンジン v1.19.0」）。エンジン版数は package.json の `engineVersion` から自動で入るので、手書きしない（シングル形態でも同じ脚注を使う）。
- 例外：絵が作品の世界観に合わない曲は、オーナー判断でコラージュから外してよい（曲目リストには載せる）。

## 運用ルール（引き継ぎ用）

このシリーズの運用ルール。制作手順とあわせて、公開・運用はこの決まりに従う。

- **コミットの author は `muse <muse@localhost>` にする。** 実際の Gmail アドレスを使うと、GitHub の email-privacy 設定で push が拒否される。
- **公開フロー**: feature ブランチ → PR → CI（check と e2e）が通ったら squash マージ → GitHub Pages の反映を確認する。main への直接 push はルールセット「protect-main」で禁止。**`[skip ci]` を付けると必須チェックが満たされずマージできなくなる**ので、文書だけの変更でも付けない。
- **版数**: `package.json` の `version` が唯一の管理場所。公開のたびに必ず上げ、納品報告に版数を明記する。形式はメジャー.マイナー.パッチ。**メジャーアップのルール：今回はリズムゲーム対応をメジャー 2 とし、全作品を 2.0.0 に数え直した**（オーナー決定 2026-11-25）。今後のメジャーアップはその都度オーナーが決めるもので、機能追加・標準化・修正ではメジャーを上げない。新作はゲームなしなら 1.0.0、ゲーム対応なら 2.0.0 から始める。マイナーは機能追加・標準化の節目で上げてパッチを 0 に戻し、パッチは修正・調整の公開ごとに上げる。**併記方式（オーナー決定 2026-11-25）**: 報告・台帳・HANDOVER の台帳ブロックには、作品の版数とあわせて、その作品が取り込んだテンプレート（エンジン）の版数を「エンジン vX.Y.Z」として併記する。エンジン版数は、その作品が最後に取り込んだテンプレート標準の版数を指し、package.json の `engineVersion` に保持する（テンプレートを取り込むたびにその版数へ更新する）。裏ジャケットの脚注（`#bc-foot`）にも、奥付と並べて作品版数とエンジン版数を併記表示する（オーナー指示 2026-11-25）。あわせて、ビルド後の dist 合計サイズも台帳レポートと台帳ブロックに記録する（オーナー指示 2026-11-25）。
- **検証の関門（デジタルCD系列の決定、2026-11-05／2026-11-21 改定）**: 公開の関門はローカル検証（`npm run verify` ＋ e2e ＋ `npm run shots` の目視）を報告することと、公開URLでのオーナーの実機確認。GitHub Actions の CI は予備の信号であり、関門そのものではない。単体HTMLプレビューは作らない（オーナー指示 2026-11-21。当初はプレビューでの実機確認だったが、以後は公開URLに統一し、納品・公開の報告には毎回URLを明記する）。
- **e2e の注意**: ポート 4173 に別リポジトリのプレビューサーバーが残っていると、`reuseExistingServer` でそちらに接続して大量に失敗する。実行前に 4173 の占有を確認し、埋まっていたら使っていないポートに変えた一時設定で回す（その変更はコミットしない）。
- **依存関係が壊れたとき**: まず `bash tools/install-v4.sh <repo>`（監査 bad:0 が基準。スクリプトはテンプレート repo の `tools/` に同梱、説明は `docs/TOOLS.md`）。個別のパッケージは `node tools/extract-one.cjs <pkg>@<ver> <dest>` で修復する。この作業 VM では実物が `~/workspace/.nk-test/` にあり、そちらを使っても同じ。
- **仮置き**: 素材が欠けていても止まらず、代用品で仮置きして作り切る。その場合、納品報告に必ず「仮置きリスト」を添え、何が仮置きで、確定には何が要るかを明記する。
- **ダッシュボード**: シリーズの現況は「デジタルCD ダッシュボード」（Muse のアーティファクト、slug `dezitarucd-datusiyubodo`）に集約されている。公開や確認の進展があったら、その場で台帳・かんばん・メトリクスを実態に合わせて更新する（後追いのまとめ更新はしない）。レビュー列の項目は、オーナーが確認して声をかけた時点で消し込み、全て終わったら完了列へ移す。
- **Dependabot PR は当面放置する**（オーナー決定、2026-11-06）。対象は開発用ツールの minor/patch 更新だけで、公開中のアプリに影響はない。各作品を次に変更するときに、ついでに取り込む。
- **エンジン改良の置き場所**: エンジン側の改良は、まずこのテンプレート repo（`mmishina-art/digitalcd-engine`）に入れる。公開済み作品へは自動では効かないので、必要な作品には個別に移植し、各作品の `docs/HANDOVER.md` に記録する。
